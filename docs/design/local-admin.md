# Local admin password rotation

Design record, 2026-11-24 (parity plan B2). Migration `0039_local_admin.sql`; agent `crates/rmm-agent/src/localadmin.rs`; protocol `crates/rmm-proto/src/localadmin.rs`; server `src/localadmin.rs`, `api/localadmin.rs`; web `LocalAdminForm.svelte`, `AgentLocalAdmin.svelte`.

One managed local administrator account per device, its password generated by the server, kept in the client's vault and rotated on a schedule, after a reveal, and on demand. Windows and Linux. macOS (`sysadminctl` and `dscl` take passwords on argv) and domain controllers report `unsupported`.

## Store first, then set

1. `vault::put_managed(kind = local_admin, reference = <agent id>, name = "Local admin: HOST", username = <account>, state = "pending")`: the previous password moves to the item's history.
2. `ServerMsg::LocalAdminSet {request_id, account, password, create}` (never queued: only sent to an online agent).
3. `AgentMsg::LocalAdminResult {request_id, ok, created, status, message}`: on `ok` the item's state becomes `current` and the next rotation is due in `rotate_days`.

A failure or a lost answer leaves the item `pending` with the password on the device in its history, so nobody is locked out. A retry (after `5 min × attempts`, up to an hour, or two minutes without an answer) sends the **same** pending password; only a finished rotation makes a new one. Only the answer to the set in flight counts. One rotation per device at a time (the tick, a connect, a policy change and Rotate now can't start two).

## Agent

- **Windows:** `NetUserGetInfo`, then `NetUserAdd` (level 1, `UF_DONT_EXPIRE_PASSWD`) or `NetUserSetInfo` level 1003, then `NetLocalGroupAddMembers` into the group whose SID is `S-1-5-32-544` (its name is looked up: it's localised). Never `net user <name> <password>`. Refused (`unsupported`) when `ProductType` is `LanmanNT`. `conflict` when Windows LAPS backs up the same account (`HKLM\SOFTWARE\Microsoft\Policies\LAPS` or `...\Windows\CurrentVersion\Policies\LAPS` with `BackupDirectory` not 0 and `AdministratorAccountName` naming it; without a name LAPS manages the built-in Administrator, which this account never is).
- **Linux:** root only; `chpasswd` with `user:password` on stdin; created with `useradd -m` and added to `sudo` or `wheel` (whichever exists) on every set. No `chpasswd`: `unsupported`.
- The password is never logged or written down; the wide-string copy on Windows and the stdin line on Linux are zeroed after use. Debug builds: `RMM_LOCALADMIN_FAKE=<file>` records sets in a JSON file instead (with `fail` and `status` knobs).

## Server

- `generate(length)`: the OS CSPRNG with rejection sampling over upper, lower, digits and `!#%+-=?@^_*.,`, no look-alikes (`I l 1 O 0`), quotes, backslash, `$`, space or `:`; at least one of each class, shuffled. 14-64 characters (default 20).
- `tick()` every `RMM_LOCALADMIN_TICK_SECS` (default 60) and on connect: online agents with the `local_admin` capability whose effective policy is on.
- `revealed(item)` (from `api/vault.rs::reveal`, any field or history entry): `next_rotate_at = min(next, now + rotate_after_reveal_hours)`, reason `reveal`.
- Turning the policy off stops rotation and leaves the account and item as they are; the card says so. Changing the account starts a first rotation of the new one.
- Without `RMM_DATA_KEY` nothing rotates.

`local_admin_state` as the plan has it, plus `request_id` and `sent_at` (the set in flight). Policy module `local_admin`, single-instance, item `00000000-0000-4000-8000-000000000006`: `{enabled: false, account: "rmmadmin", create: true, rotate_days: 30, length: 20, rotate_after_reveal_hours: 24}`; turn it on by overriding `enabled` in a set (Windows workstations, say). Editing it needs `vault.manage`; built-in names (`administrator`, `root`, `guest`...) are refused.

## API, audit, alerts

`GET /agents/{id}/local-admin` (policy, state, the item's managed state; the item id only for people who may open the vault), `POST /agents/{id}/local-admin/rotate` (technician with `vault.manage`). Not in the public API. Audited: `local_admin.rotate` (trigger `first`, `schedule`, `reveal`, `manual`; a retry of the same password only when someone asked) and `local_admin.result` (ok, created, status, message), plus `vault.system_write`. Never the password.

Alert kind `local_admin`, params `{overdue_days: 7}`: one alert per device when the rotation `failed`, is in `conflict`, or is that many days past due. `unsupported` doesn't alert.

UI: the policy set's Local admin section, a Local admin card on the device overview (account, last and next rotation, status, error, Show password, Rotate now), and the managed items in the client's Passwords tab.
